# PrestaShop Integration Module — Specification

**Status of prior deliverables:** WooCommerce, Shopify, and Magento 2 Integration Module Specifications — **APPROVED / drafted**, ready for handover.

**Roadmap status:** This is a **Tier 2 connector spec**, prepared ahead of build for planning purposes. The MVP build sequence remains WooCommerce/Shopify × Dinero/e-conomic (Tier 1) as previously agreed — this document does not change that sequence.

**This document:** Connector-level specification for the PrestaShop source module, following the same structure as the prior connector specs — API approach, entity coverage, accounting mapping model, VAT handling, sync execution modes, field-level sync selection, and value-add features. Specification only — no implementation.

---

## 1. API approach

PrestaShop's integration story is the most constrained of the four connectors specified so far, and this needs to be designed for honestly rather than assumed away.

- **The legacy Webservice API** (`/api/` gateway) is the stable, full-coverage option — REST-style CRUD (GET/POST/PUT/DELETE/HEAD) over most store resources, XML by default. It's been stable for over a decade and remains fully functional in the current major version — **this should be the module's primary integration surface** for MVP-equivalent Tier 2 coverage.
- **PrestaShop 9 introduces a new AdminAPI** (OAuth2, JSON, Symfony/API Platform-based) alongside the legacy Webservice. It's cleaner but **coverage is still growing and does not yet match the legacy Webservice's full resource set** — not yet a safe primary choice; worth revisiting as it matures, but the legacy Webservice is the pragmatic pick today.
- **No native outbound webhooks for store events** (orders, products, stock) in the core platform. What PrestaShop calls "webhooks" is tied to PrestaShop Billing, a separate paid service focused on billing events — not general store-event webhooks. Real-time push requires either a **custom companion module** installed on the merchant's store (using PrestaShop's internal hook system, e.g. `hookActionProductUpdate`, to POST to an external endpoint) or accepting **polling as the default and only mechanism**.

**This means PrestaShop's default sync posture is polling-only**, same category as Magento Open Source (§1 of that spec) and conceptually similar to how Uniconta is already handled elsewhere in the platform's design. A companion module for webhook-style push is a real option worth offering later as an enhancement, but it adds a genuine onboarding step (merchant installs a module in their PrestaShop back office) that doesn't exist for WooCommerce, Shopify, or Adobe Commerce — **don't assume this in the MVP-equivalent Tier 2 default experience.**

**Practical implication for the sync engine**: poll interval choice matters more here than on any other connector so far, since it's the primary (not fallback) mechanism. Recommend a shorter default polling interval for this connector specifically (e.g., 15–30 minutes rather than hourly) to keep order-capture latency reasonable given there's no real-time path by default.

## 2. Authentication & connection

- **Auth method**: Webservice API key, generated by the merchant in their PrestaShop back office (Advanced Parameters → Webservice), used as HTTP Basic Auth (key as username, blank password).
- **Connection wizard step**: merchant pastes their store URL + API key. Validate immediately with a lightweight `GET /api/products?limit=1` call before saving.
- **Permission scoping**: the Webservice key's resource permissions are configured per-resource in the PrestaShop back office at key-creation time — the wizard should instruct the merchant which specific resources to grant read access to (orders, customers, products, credit slips, stock_availables), consistent with the least-privilege pattern used across the other connector modules.

## 3. Entity coverage

| Entity | PrestaShop source | Sync direction | Notes |
|---|---|---|---|
| Orders | `orders` resource | Read | Line items via `order_details`, tax, discounts, shipping, payment |
| Credit Slips (Refunds) | `order_credit_slips` (referred to as "credit slips" in PrestaShop's own terminology) | Read | Maps directly to ERP credit notes |
| Customers | `customers` resource | Read | Guest checkout handling — same pattern as WooCommerce/Magento |
| Products | `products` resource + `categories` | Read | Multiple categories per product, same complexity as WooCommerce/Magento |
| Stock levels | `stock_availables` resource | Read | Single-warehouse by default; multi-warehouse/advanced stock management is a separate PrestaShop feature — see §9 |

## 4. Custom accounting mapping model

### 4.1 Mapping hierarchy

Same "most specific wins" model as the other three connectors: **category-level default → product-level override → fallback account**, with income split at the line-item level (§4.2). PrestaShop products can belong to multiple categories, same ambiguity pattern as WooCommerce and Magento — same resolution: merchant designates a primary category per product at mapping time.

### 4.2 Line-item-level mapping

Same principle carried through consistently across all four connector specs: each order line posts to its own mapped account.

### 4.3 Non-product line items

Shipping cost and discount/voucher amounts need their own default account mapping, consistent with the pattern established across the other connectors.

## 5. VAT / tax handling

PrestaShop supports tax rules per product (via tax rule groups) and country/state-based tax calculation, broadly comparable to WooCommerce's model rather than Magento's more explicit B2B VAT-ID validation. **Same three-level override model applies unchanged:**

1. Store-level default (PrestaShop's configured tax rules)
2. Category-level override
3. Product-level override

Same conflict-flagging behavior as the other specs: if an override marks something exempt but PrestaShop's own order data still shows tax, flag for merchant review rather than trusting either source blindly.

**Reverse-charge / B2B VAT**: PrestaShop doesn't have Magento's native VAT-ID-validation package built in — B2B VAT ID capture typically depends on the merchant's specific module choice (several are common in the PrestaShop ecosystem, none universal). Recommend treating reverse-charge routing as phase-2 for this connector specifically, with **no early-mover advantage the way Magento has** — the underlying VAT ID data isn't guaranteed to exist in a consistent field across merchant installs, so this needs its own investigation whenever it's prioritized rather than being assumed available.

## 6. Value-add features worth including

| Feature | Value proposition |
|---|---|
| **Polling-first sync design** | Given no native webhooks (§1), the sync engine's polling reliability is this connector's single most important design point — invest in a shorter default interval and robust change-detection rather than treating polling as a fallback path |
| **Guest checkout customer handling** | Same pattern as WooCommerce/Magento — order-level billing data used regardless of registered customer status, matched by email to avoid duplicates |
| **SKU-based (reference-based) product matching** | PrestaShop calls this field "reference" rather than SKU, but the concept and value proposition are identical — reduces onboarding friction for large catalogs |
| **Credit slip handling at line-item granularity** | Same principle as the other connectors' refund handling |
| **Optional companion module for real-time push** | Flagged as a genuine future enhancement (§1) rather than MVP-equivalent default — worth scoping properly once there's demand, since it changes the onboarding flow meaningfully |
| **Sync execution modes and manual sync controls** | Same three-mode model and manual controls as the other three connectors — see §7 |

## 7. Sync execution modes & manual sync controls

Same confirmed requirement and identical behavior to the WooCommerce, Shopify, and Magento modules — reused without variation.

### 7.1 Three execution modes

1. **Dry-run** — pure simulation, nothing written to the ERP. Surfaces forecasted mapping/VAT issues before anything real happens.
2. **Draft sync** — transfers data to the ERP as **draft/unapproved entries**, pending manual bookkeeper approval.
3. **Live sync** — posts directly as final, approved ERP entries.

**Same dependency flag as the other three specs**: draft-mode posting depends on Dinero and e-conomic's write APIs supporting an unposted/draft state — to be confirmed at the ERP-module spec stage.

### 7.2 Manual sync — period selection and overwrite control

Identical mechanism to the other connectors: developer-layer control for date-range-scoped manual sync, with **overwrite existing** vs. **skip existing** toggle.

## 8. Field-level sync selection

Same Required/Optional/Default pattern as the other three connectors, reused so all four share one manifest structure.

### 8.1 Customers

| Field | Required / Optional | Default | Notes |
|---|---|---|---|
| Name (first/last or company) | Required | On | |
| Email | Required | On | Guest-checkout matching key, same pattern as other connectors |
| Address (incl. country) | Required | On | Country needed for VAT logic |
| Phone | Optional | On | |
| Company name / VAT number (if captured) | Optional | On | Not guaranteed present depending on merchant's module setup (§5) |
| Newsletter/opt-in status | Not exposed | — | No accounting/ops value |
| Custom fields (if merchant uses a custom-field module) | Optional, merchant-specified | Off | |

### 8.2 Orders

| Field | Required / Optional | Default | Notes |
|---|---|---|---|
| Order reference, date, currency | Required | On | |
| Line items (product, qty, price, tax) | Required | On | Core to §4.2 line-item-level posting |
| Order totals (subtotal, tax, total, discount) | Required | On | |
| Customer reference | Required | On | |
| Order status | Required | On | Drives the order-status sync filter, same as other connectors |
| Payment method | Optional | On | |
| Carrier/shipping method | Optional | On | |
| Voucher/discount code | Optional | On | |
| Order message/note | Optional | Off | |

### 8.3 Products

| Field | Required / Optional | Default | Notes |
|---|---|---|---|
| Reference (SKU equivalent), name | Required | On | |
| Price | Required | On | |
| Category (primary, per §4.1) | Required | On | |
| Tax rule group | Required | On | Drives VAT resolution (§5) |
| Weight | Optional | Off | Only relevant if the ERP tracks logistics |
| Custom fields | Optional, merchant-specified | Off | |

### 8.4 Stock & Credit Slips

- **Stock levels**: available quantity is Required if Stock entity is enabled. PrestaShop's core stock model is single-warehouse by default — multi-warehouse (Advanced Stock Management) is a distinct, less universal feature, so per-location breakdown isn't offered as a field option here the way it is for Shopify/Magento; flagged separately in §9 if needed later.
- **Credit slips**: refunded amount, date, and refunded line items are Required. Refund reason/comment is Optional, default off.

### 8.5 Custom fields

Same mechanism as the other connectors: merchant names a specific custom field (exact key/attribute, verified via test lookup), mapped to a chosen ERP custom field. Optional, off by default, developer-layer feature. Worth noting this is less standardized in PrestaShop than in WooCommerce/Magento/Shopify, since custom fields typically come from whichever third-party module the merchant has installed rather than a single core mechanism — expect more variance here than on other connectors.

## 9. Explicitly out of scope for MVP (PrestaShop module)

| Feature | Why deferred |
|---|---|
| Real-time webhook-driven sync via companion module | Genuine future enhancement (§1, §6), not default — requires its own scoping and merchant-side installation step |
| Advanced Stock Management (multi-warehouse) | Distinct PrestaShop feature, not universally enabled — single-location aggregated stock is the MVP-equivalent default |
| Reverse-charge VAT routing | Deferred with no early-mover advantage here, unlike Magento (§5) |
| PrestaShop 9 AdminAPI as primary integration surface | Not yet at resource-coverage parity with the legacy Webservice — revisit once it matures, don't build against it as primary today |
| Multi-shop (PrestaShop's built-in multistore feature) | Real merchant pattern, but adds mapping complexity (per-shop category/tax rules) — treat as a distinct future design pass, same treatment as Magento's multi-store/multi-website deferral |
