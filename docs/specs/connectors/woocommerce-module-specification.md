# WooCommerce Integration Module — Specification

**Status of prior deliverable:** Sitemap & Page Specifications — **APPROVED**, ready for handover.

**This document:** Connector-level specification for the WooCommerce source module, covering entity coverage, custom accounting mapping, VAT handling, field-level sync selection, and value-add features. Specification only — no implementation.

---

## 1. Why WooCommerce needs more design attention than a typical connector

WooCommerce isn't a hosted SaaS API like Shopify — it's a self-hosted WordPress plugin with a REST API (`/wp-json/wc/v3`) whose behavior depends heavily on the merchant's specific plugin stack (tax plugins, multi-currency plugins, subscription plugins, stock/warehouse plugins). This has two consequences for the spec:

- The **core module** should target what's available in the core WooCommerce REST API v3 — Orders, Products, Product Categories/Variations/Attributes, Customers, Order Refunds, Taxes/Tax Classes, Webhooks, Coupons — since that's guaranteed present regardless of the merchant's plugin choices.
- Anything dependent on a specific third-party plugin (multi-warehouse stock, WooCommerce Subscriptions, multi-currency) should be flagged as **plugin-dependent, phase-2 scope**, not baked into the core manifest, since you can't assume a given merchant has it installed.

## 2. Authentication & connection

- **Auth method**: REST API Consumer Key/Secret pair, generated by the merchant in WooCommerce → Settings → Advanced → REST API. Basic Auth over HTTPS (recommended) or OAuth 1.0a if the store is HTTP-only.
- **Connection wizard step**: merchant pastes their store URL + consumer key + secret. Validate immediately with a lightweight `GET /wp-json/wc/v3/system_status` or similar call before saving, so connection errors surface at setup time, not on the first sync attempt.
- **Webhooks vs. polling**: WooCommerce supports native webhooks (order created/updated, product updated, customer created, etc.), delivered as signed HTTP POST (`X-WC-Webhook-Signature`, HMAC-SHA256). **Recommend webhook-driven sync as primary mechanism** for near-real-time order capture, with a scheduled polling fallback (e.g., hourly) to catch any missed deliveries — WooCommerce disables a webhook automatically after 5 consecutive failed deliveries, so a polling safety net protects against silent sync gaps if that happens.
- **Webhook registration**: done programmatically at integration setup via the Webhooks API — no manual merchant configuration required, which keeps the "business owner friendly" promise from the integrations page design.

|---|---|---|---|
| Orders | Orders API | Read (WooCommerce → ERP) | Includes line items, shipping, fees, discounts, tax breakdown, payment method |
| Order Refunds | Order Refunds API | Read | Maps to ERP credit notes |

## 4. Custom accounting mapping model (core requirement)

This is the centerpiece of the module, per your stated purpose: letting merchants map WooCommerce products/categories to specific ERP account lines so income can be automatically categorized by activity type.

### 4.1 Mapping hierarchy (most specific wins)

1. **Category-level default** — a WooCommerce product category maps to a default ERP account line (e.g., "Electronics" → account 1010, "Services" → account 1020)
2. **Product-level override** — an individual product can override its category's default and map to a different account line
3. **Fallback/unmapped default** — a single "catch-all" account for any product not yet categorized or mapped, so sync never fails outright on a missing mapping — it posts to the fallback and flags it for the merchant to review

This mirrors the mapping UI already scoped on the integrations detail page (category defaults + per-product override table), so no new UI concept is needed — this is the data model behind that UI.

### 4.2 Handling product category complexity

WooCommerce products can belong to **multiple categories** (unlike a single-parent structure). The mapping model needs an explicit rule for this — recommend:

- Merchant designates one category per product as the "primary" category for accounting purposes (a simple dropdown at mapping time, defaulting to the first/lowest-ID category), rather than the sync engine guessing
- This avoids ambiguous or duplicate income postings when a product sits in both "Electronics" and "Black Friday Deals," for example

### 4.3 Line-item-level mapping, not just order-level

Since a single WooCommerce order can contain products from multiple categories, the ERP posting needs to be **split at the line-item level** — each order line posts to its own mapped account, not the whole order to one account. This is what actually enables "automated finance based on activity type" as you described — a single order becomes multiple correctly-categorized ledger lines, not one lump sum.

### 4.4 Non-product line items also need mapping

Orders include more than product lines — shipping fees, custom fees, and discounts all need their own account mapping (typically simpler: one default account each, since these aren't usually category-specific), so the full order reconciles to the correct total in the ERP.

## 5. VAT / tax handling

This is a first-class requirement, not an edge case, given your Nordic/DACH target market.

### 5.1 What WooCommerce provides

- Each order line item includes tax detail: `subtotal_tax`, `total_tax`, and a `taxes` array with rate ID, subtotal, and total per applicable tax rate
- Tax rates/classes are separately queryable via the Taxes and Tax Classes APIs — useful for validating rate consistency, but the order payload already contains the applied amounts, so live sync doesn't need to re-look-up rates

### 5.2 Module behavior

- **VAT applicability, not just include/exclude presentation** — confirmed this needs to go further than a gross/net display toggle. WooCommerce itself has a single store-wide "enable taxes" setting, but real merchants run mixed catalogs against it (e.g., a subscription-based merchant charging VAT on physical/standard goods but selling VAT-exempt subscription items in the same store). The mapping model needs a **three-level VAT override**, mirroring the accounting mapping hierarchy in §4.1:
  1. **Store-level default** — inherited from the WooCommerce global tax setting (VAT on/off) as the baseline
  2. **Category-level override** — a specific category can be flagged VAT-exempt (or VAT-applicable) regardless of the store default — this is what covers the subscription-items-are-VAT-exempt scenario
  3. **Product-level override** — an individual product can override its category's VAT setting, same precedence pattern as the account mapping
  - When VAT applies (at whichever level resolves), the module posts gross/net per the merchant's chosen presentation, with VAT posted to its own ERP account line — standard Nordic/DACH bookkeeping practice, not embedded in revenue
  - When VAT is overridden to exempt at category/product level but WooCommerce's own order payload still shows a tax amount on that line (e.g., merchant misconfigured a product's tax class in WooCommerce itself), the module should flag this as a mapping conflict for merchant review rather than silently trusting either source — this is a real data-integrity gap worth catching before it reaches the ledger
- **Multi-rate orders**: since a single order can contain lines taxed at different rates (e.g., standard rate + reduced rate for certain goods), the split-at-line-item approach from §4.3 naturally handles this — each line carries its own tax detail already
- **Reverse charge / cross-border VAT (DACH/EU consideration)**: flag as a mapping rule, not core-engine logic — if a customer's billing country differs from the merchant's and B2B VAT ID is present, the merchant may want that order routed to a different account (reverse-charge). Recommend this as a **phase-2 mapping rule** (conditional routing based on customer country/VAT ID) rather than MVP, but worth designing the mapping schema so this condition can be added without restructuring it later.

## 6. Value-add features worth including (beyond bare entity sync)

These are the things that would make this genuinely useful to a WooCommerce merchant beyond just moving data, in rough priority order:

| Feature | Value proposition |
|---|---|
| **Order status filtering** | Let the merchant choose which WooCommerce order statuses trigger a sync (e.g., only "processing"/"completed", not "pending payment" or "cancelled") — avoids posting unpaid or abandoned orders to the ERP |
| **Guest checkout customer handling** | Confirmed: guest checkout orders (no `customer_id`) still carry real customer data via the order's billing/shipping address block (name, email, address) and this must transfer to the ERP like any other customer — a guest is not "no customer," just not a registered WooCommerce account. See §6.1 for the mapping detail |
| **SKU-based product matching** | Match WooCommerce products to existing ERP items by SKU where possible, rather than requiring every product to be manually mapped — significantly reduces onboarding friction for merchants with large catalogs |
| **Partial refund handling** | WooCommerce refunds can be partial (specific line items or amounts) — the credit note sync needs to reflect exactly what was refunded, at the same line-item granularity as the original order, not just a lump-sum credit |
| **Discount/coupon transparency** | Show discount amounts as their own line in the ERP posting (not silently netted into product revenue) — merchants doing sales/promo analysis in their ERP will want this visible |
| **Product variation handling** | Variable products (e.g., a T-shirt in multiple sizes/colors) should map at the parent-product or category level by default, with the option to map individual variations separately if a merchant needs that granularity — most won't, so don't force it |
| **Payment method → account mapping** | Optional: map payment method (card, bank transfer, PayPal, etc.) to different ERP accounts if the merchant reconciles by payment channel — common ask from finance-conscious merchants, low implementation cost given it's already on the order payload |
| **Multi-currency awareness** | Store the order currency and flag mismatches against the ERP's base currency rather than silently assuming same-currency — WooCommerce core is single-currency per store, but many EU merchants run multi-currency via a plugin, so at minimum surface the currency field and let the merchant know if it's unmapped |
| **Sync execution modes** | Merchants and developers need more than a binary "preview vs. live" choice — see §7 for the full dry-run / draft-post / live-sync model |

### 6.1 Guest checkout — customer mapping detail

Every WooCommerce order — guest or registered — carries a billing address block (name, email, phone, address) on the order itself, independent of whether a `customer_id` exists. The module treats this as the customer data source in both cases, with one behavioral difference:

- **Registered customer** (`customer_id` present): sync/update the ERP customer record keyed to that WooCommerce customer ID, so repeat orders update one ERP record rather than duplicating it.
- **Guest checkout** (`customer_id` = 0): still create/update a real ERP customer record from the order's billing data — not a generic placeholder. To avoid flooding the ERP with duplicate one-time customer records for repeat guest shoppers (same person checking out as guest multiple times), **match on email address** before creating a new ERP customer: if an ERP customer with that email already exists (whether originally created as a guest order or a registered one), attach the new order to it instead of creating a duplicate.
- This means the customer entity manifest needs an email-based lookup/upsert as its core matching strategy, not just a straight `customer_id`-keyed create — this applies to both guest and registered paths uniformly, which keeps the logic simple rather than branching.

## 7. Sync execution modes & manual sync controls

Confirmed requirement: sync isn't a single binary action. The module supports three distinct execution modes, plus developer-facing controls for scoping and re-running syncs manually.

### 7.1 Three execution modes

1. **Dry-run** — pure simulation. Nothing is written to the ERP. Walks through mapping and VAT resolution for the selected data and surfaces forecasted issues before anything real happens: unmapped categories/products, VAT conflicts (§5.2), missing required customer fields, currency mismatches, and similar. This is the existing "sync preview" concept from §6, now formalized as one of three modes rather than a standalone feature.
2. **Draft sync** — actually transfers data to the ERP, but posts it as **draft/unapproved entries** rather than final ledger postings. A bookkeeper reviews and manually approves each line inside the ERP itself before anything becomes a final posting. This is a real data transfer with a human checkpoint before finality — distinct from dry-run (no data movement) and live sync (final on arrival).
3. **Live sync** — posts directly as final, approved ERP entries. This is the default/existing behavior assumed everywhere else in this spec.

**Dependency flag**: draft-mode posting depends on whether Dinero and e-conomic's write APIs actually support creating entries in a draft/unposted state. This needs to be confirmed at the ERP-module spec stage (Dinero, then e-conomic) — if either API only supports direct-final posting, draft mode for that specific ERP target may not be achievable as designed, and would need a documented fallback (e.g., emulating "draft" as a WooCommerce-integration-side hold rather than an ERP-native draft).

### 7.2 Manual sync — period selection and overwrite control

In addition to the entity-level "sync now" trigger on the integration detail page, developers get access to a manual sync control with two parameters:

- **Period selection**: choose a specific date range to sync, rather than only the default "latest/unsynced records" behavior. Useful for backfills, re-running a specific week/month after a mapping fix, or catching up after a connection was paused.
- **Overwrite toggle**: for the selected period, choose between:
  - **Overwrite existing** — re-push and update records that were already synced in that period (e.g., after correcting a mapping error, to fix records that already posted incorrectly)
  - **Skip existing** — only sync new/missing records in that period, leaving already-synced records untouched (the safer default, avoiding accidental duplication or clobbering of correct data)

Both controls apply to all execution modes (§7.1) and to both WooCommerce and Shopify uniformly — this is sync-engine/UI behavior, not connector-specific, and belongs in the developer/advanced layer of the integration detail page alongside the existing retry/replay controls.

## 8. Field-level sync selection

Not every field WooCommerce exposes belongs in the ERP, and merchants will differ on what they consider useful (a two-person shop may not care about tracking payment method per order; a larger merchant reconciling by channel will). Rather than a fixed field set per entity, each entity's manifest declares fields as **Required** (always synced — the ERP record isn't valid without them) or **Optional** (merchant can select/deselect), with sensible defaults pre-checked so a business owner never has to make this decision if they don't want to.

**UI placement**: this lives inside Step 4 of the integration wizard (entity selection, per the sitemap) as an expandable "Customize fields" panel under each enabled entity, and remains editable afterward from the integration detail page's business-owner layer — not buried in the developer layer, since field selection is a business decision (e.g., "do we want customer phone numbers in the ERP?"), not a technical one. The developer layer separately exposes the raw WooCommerce field key alongside each toggle, for anyone who wants that detail.

### 8.1 Customers

| Field | Required / Optional | Default | Notes |
|---|---|---|---|
| Name (first/last or company) | Required | On | ERP customer record isn't valid without it |
| Email | Required | On | Also the guest-checkout matching key (§6.1) |
| Billing address (incl. country) | Required | On | Country needed for VAT logic (§5.2, reverse-charge design) |
| Phone | Optional | On | Common but not universally needed |
| Shipping address (if different from billing) | Optional | On | Skip if ERP only tracks one address per customer |
| Company name / VAT ID (B2B) | Optional | On | Relevant for DACH B2B merchants specifically |
| Customer note / internal note | Optional | Off | Rarely relevant to accounting |
| WooCommerce username, avatar, account dates | Not exposed | — | No accounting/ops value — not offered as a field at all, to avoid clutter |
| Custom `meta_data` keys | Optional, merchant-specified | Off | Merchant can name specific custom field keys from their store to include (see §8.5) |

### 8.2 Orders

| Field | Required / Optional | Default | Notes |
|---|---|---|---|
| Order number, date, currency | Required | On | Core to any valid voucher/invoice |
| Line items (product, qty, price, tax) | Required | On | Core to §4.3 line-item-level posting |
| Order totals (subtotal, tax, total, discount) | Required | On | |
| Customer reference | Required | On | Links to §8.1 customer record |
| Payment method / method title | Optional | On | Needed only if payment-method-to-account mapping (§6) is used |
| Transaction ID | Optional | Off | Useful for reconciliation against payment processor statements, not universally needed |
| Shipping method label | Optional | On | |
| Coupon code(s) used | Optional | On | Reference text alongside the discount amount |
| Customer order note | Optional | Off | Free-text note from checkout — rarely accounting-relevant, occasionally useful context |
| Custom `meta_data` keys | Optional, merchant-specified | Off | E.g., a merchant's custom checkout field |

### 8.3 Products

| Field | Required / Optional | Default | Notes |
|---|---|---|---|
| SKU / product ID, name | Required | On | Needed for §6 SKU-matching and line-item description |
| Price (regular/sale) | Required | On | Needed for accurate order-line posting |
| Category (primary, per §4.2) | Required | On | Drives the account mapping |
| Tax class / tax status | Required | On | Drives VAT resolution (§5) |
| Short description | Optional | Off | No accounting value, occasionally wanted for ERP item descriptions |
| Weight / dimensions | Optional | Off | Only relevant if the ERP tracks logistics data |
| Images | Not exposed | — | No accounting/ops value for this connector's purpose |
| Tags, attributes | Optional | Off | Useful for merchants doing detailed catalog-level reporting in the ERP |
| Product permalink (store URL) | Optional | Off | Nice-to-have as a reference link on the ERP item record |
| Custom `meta_data` keys | Optional, merchant-specified | Off | |

### 8.4 Stock & Refunds

- **Stock levels**: `stock_quantity` is the only field with real value here — Required if the Stock entity is enabled at all. `stock_status` (in stock/out of stock/on backorder) offered as Optional, default off, since most ERPs work off quantity rather than status text.
- **Refunds**: amount, date, and refunded line items are Required (mirrors the original order's line-item structure, per §6). Refund reason and staff member who processed it are Optional, default off — internal WooCommerce context, rarely needed in the ERP.

### 8.5 Custom fields (`meta_data`)

WooCommerce allows arbitrary custom fields on customers, orders, and products via `meta_data`, which varies per merchant (custom checkout plugins, CRM tags, etc.) and can't be predicted in the connector manifest. Recommend a simple mechanism: the merchant can name a specific `meta_data` key (by typing the exact key, with a "test lookup" button that confirms it exists on a real sample record) and choose which ERP custom field it maps to. This stays optional and off by default, and is realistically a developer-layer feature rather than something surfaced to a typical business owner.

## 9. Explicitly out of scope for MVP (WooCommerce module)

| Feature | Why deferred |
|---|---|
| Multi-warehouse/location stock sync | Requires a third-party plugin (e.g., ATUM, Stock Manager) — no consistent core API |
| WooCommerce Subscriptions plugin support (recurring orders) | Separate plugin, separate API surface — real opportunity later given your own platform's subscription model, but not core MVP |
| Reverse-charge/conditional VAT routing | Design the schema to support it (§5.2), but don't build the conditional logic yet |
| Product review sync | No accounting or ops value, skip entirely |
| Bidirectional stock write-back (ERP → WooCommerce) | Read-direction (WooCommerce stock → ERP) is the safer, simpler MVP direction; write-back risks overselling if not carefully sequenced against order processing — treat as a distinct future feature with its own risk review |
