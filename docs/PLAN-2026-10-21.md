## 4. Filtre som URL-state

Én hjælper, `useUrlFilter(key, values, default)` i `apps/web/src/components/platform/`, bygget på de eksisterende `QueryFilters`/`PeriodPills`:

- Den skriver med `router.replace` (ingen ny historikpost ved filterskift) og bevarer andre parametre.
- Serveren læser og validerer alle parametre. Ukendte værdier giver standardværdien, aldrig en fejl.
- Ændringer annonceres i en `aria-live="polite"`-region, fx "Viser Arkiv · 412 sager". Den segmenterede kontrol er `role="radiogroup"` med `aria-checked`, eller links med `aria-current`, alt efter om den navigerer.

| Side | Parameter | Standard | Bemærkning |
|---|---|---|---|
| Sager | `view=board\|list\|archive` | `board` (mobil: `list`) | Tavlens klient-filtre (`q`, `mine`, `priority` …) flyttes også til URL, så de overlever reload. Arkivets eksisterende parametre bevares. "Arkiv · 412" er et tal fra data |
| Fejl | `period=24h\|7d\|30d` eller `from`/`to` (YYYY-MM-DD) | `24h` | `from`/`to` vinder over `period`. `to` er inklusive, og `from` må højst være `to`. Højst 90 dage (§9 Q14). Datovælgeren bruger `<input type="date">` |
| Tidsforbrug | `scope=me\|team\|customer`, `week=` | `me` | De gamle ruter `/time/team` og `/time/customers` bliver til ét view. Den gamle toggle "Mig/Hele teamet" fjernes (S6). Rettighederne er som i dag (alle staff må se team og pr. kunde) |
| Rapporter | sti `revenue\|support\|invoicing`, `from`, `to` | indeværende måned | Typen er et link (sti), ikke en parameter, som i rutekortet |
| Adgange | `filter=mine\|all` | `mine` | |
| Fakturering (F6/MP22) | `status=` | alle | MP07 Forfaldne = `status=overdue` |

## 5. Datamodel (nye migrationer fra 0046, PG12-kompatible)

Alle nye migrationer følger mønstret: Drizzle-DDL plus en håndskrevet `*_security.sql`. De bruger ingen PG13+-funktioner (ingen `gen_random_uuid()` uden pgcrypto, `app.uuid_v7()` som standard-id). Nye public-tabeller registreres i `packages/db/src/tables.ts` og får fixtures i isolation-suiten.

### 5.1 Prisversioner (A2/MP26)

```
platform.price_versions
  id uuid pk default app.uuid_v7()
  kind text check (kind in ('plan','support'))
  plan_id text null references plans(id)       -- null når kind='support'
  price_monthly_ore int null                    -- plan, ekskl. moms
  support_rate_ore int null                     -- support, ekskl. moms (inkl. beregnes ×1,25 i UI)
  entitlements jsonb not null default '{}'      -- snapshot af planens entitlements og features
  settings jsonb not null default '{}'          -- support: rounding_minutes, billing_rule, non_billable[]
  applies_to text check (applies_to in ('new','all_from_renewal'))
  effective_from timestamptz not null
  created_by uuid, created_by_name text, created_at timestamptz
  notice_sent_at timestamptz null
subscriptions.price_version_id uuid null references platform.price_versions(id)
```

- **Backfill:** én version pr. plan med dagens pris og entitlements (`effective_from` = migrationstid). Alle eksisterende abonnementer peger på den.
- **Gem** (`app.platform_price_version_create`, security definer, kun superadmin) opretter én version for hver ændret plan eller supportpris. Den opdaterer `plans.price_monthly_ore`/`plan_entitlements` til den nyeste version, så signup og planvalg (`MA33`, D13) uændret læser "aktuel pris". Alt skrives i `platform.audit` (`price_version.created`, med før og efter).
- **Opkrævning** (`subscriptionPriceOre`) læser prisen fra abonnementets `price_version_id`, ikke fra planen. Nye abonnementer får nyeste version. Det rører kun den linje i signup-flowet, der vælger pris (§9 Q17).
- **"Alle fra næste fornyelse":** et worker-job sender e-mail til ejeren (skabelon i `packages/i18n`, ingen løfter, kun ny pris og dato). Ved første fornyelse efter `effective_from`, og tidligst 30 dage efter besked (§9 Q5), flyttes abonnementet til den nye version. Det audit-logges i kundens log.
- **Supportpris:** `finance`-beregningen (0045 og `core/src/finance.ts`) læser satsen og oprundingen for den måned, der afregnes, fra nyeste `kind='support'`-version med `effective_from <= periodens start`. "En ny timepris gælder fra næste afregningsperiode" betyder `effective_from` = den 1. i næste måned. Konstanterne `DEFAULT_SUPPORT_RATE_ORE` og `BILLING_STEP_MINUTES` bliver kun fallback i tests, og fallbacken på 64000 i SQL fjernes efter backfill.
- **Historik** er et panel med version, ikrafttræden, hvem og hvad der ændredes.
- **Felter på A2, der ikke findes i data i dag:** `trial_days` (14/14/null="Efter aftale"), `ean_invoice` (feature), `external_users`, `sso`, `white_label`, `more_destinations` (findes som features). De tilføjes som entitlement-nøgler i whitelist'en. `[ANTAL]` vises, hvor værdien er null *og* tegnefladen viser `[ANTAL]` (Startup integrationssæt, brugere og opbevaring), indtil der er data (§9 Q4).

### 5.4 Profil og avatar

```
app.user_profiles
  user_id uuid pk references auth.users
  given_name text, family_name text, phone text, time_zone text, title text, city text null
  avatar_key text null, avatar_updated_at timestamptz null
  -- RLS: restrictive user_id = app.current_user_id() (skriv og læs). Navn og avatar-hash læses af
  --       andre gennem eksisterende visninger (team, audit), ikke direkte fra tabellen.
-- avatar_key i user_profiles: "avatars/<user_id>/<sha256>.webp" i lagerområdet (se nedenfor)
```

- `auth.users.name` holdes i sync ("fornavn efternavn"), så alle eksisterende visninger virker. `locale` bliver i `auth.users`.
- **Upload** (server action, kun egen bruger): højst 5 MB. Typen tjekkes fra de magiske bytes (PNG/JPEG), ikke fra `Content-Type`. Billedet skal være mindst 256 × 256. Det dekodes, EXIF fjernes, det beskæres til kvadrat, skaleres til 512 px og gemmes som WebP. Det gamle billede overskrives eller slettes. `profile.avatar_changed`/`profile.avatar_removed` logges i kundens audit-log (kunde) eller `platform.audit` (staff).
- **Lagerområde (besluttet, Q1):** en ny pakke `packages/storage` med en lille grænseflade (`put`, `get`, `delete`, `exists`) og én driver til disk, rodmappe fra `STORAGE_DIR` (produktion `/var/lib/agentor/storage`, ejet af `agentor-web`, mode 0750; dev og e2e en mappe under `.data/`). Nøgler valideres (kun `[a-z0-9/-_.]`, ingen `..`, altid under roden), så stier ikke kan slippe ud. Grænsefladen gør det muligt at skifte til en S3-kompatibel bucket senere uden at røre kaldene.
  - Avatarer ligger under `avatars/<user_id>/<sha256>.webp`. Ved udskiftning skrives det nye først, `user_profiles.avatar_key` opdateres i samme transaktion som audit-rækken, og derefter slettes den gamle fil. Et oprydningsjob fjerner filer uden reference.
  - `server-setup.sh` opretter mappen og `deploy.sh` tjekker, at den findes og er skrivbar. pgBackRest dækker kun databasen, så mappen skal med i serverens backup (opfølgning i `infra/ops/README.md`).
  - Filerne serveres kun gennem `/api/avatar/[userId]` med adgangstjek og ETag, aldrig som statiske filer.
- **Billedbehandling (anbefaling, Q1):** `sharp` som direkte afhængighed i `apps/web`, i samme version som Next allerede har i lockfilen (0.35.5). Den er standardbiblioteket til billeder i Node, Next bruger den selv til billedoptimering, og den kan dekode PNG/JPEG, rotere efter EXIF og fjerne EXIF, beskære, skalere og kode WebP i ét kald. Alternativerne i ren JavaScript (fx `jimp`) er langsommere, har ingen god WebP-koder og er mindre brugte. Afhængigheden tilføjes først, når du har sagt ja.
- **Visning:** `Avatar` i `packages/ui` får `src?` og falder tilbage til initialer. Billedet vises for teamet (samme tenant) og i audit-loggen. Staff ser kundebrugeres avatar kun under en aktiv supportadgang til tenanten.

### 5.5 Engagement og aktivitetskort

Kilde: **eksisterende audit- og hændelsestabeller**, beregnet ved læsning. Ingen ny sporing, ingen ny tabel.

- **Staff:** pr. dag antal løste sager (`case_events` kind=status til resolved, `author_user_id`) + supportsessioner (`support_sessions.started_at`).
- **Kunde:** pr. dag antal `audit_log`-hændelser med `actor_user_id` = brugeren og `actor_kind='user'` i den aktive tenant for kørsler (`flow.run_requested`), gentagelser (`flow.retried`) og indstillinger (`security.updated`, `notifications.updated`, `company.updated`, flow-ændringer).
- **Niveauer:** 0 = ingen, og 1–4 er kvartiler af brugerens egne dage med aktivitet i de 84 dage. Så kortet er personligt og ikke en sammenligning med andre.
- **Stime:** staff "dage i træk med løste sager", med bedste stime inden for audit-loggens opbevaring (24 måneder).
- **Personfølsomhed:** dataene vises kun for brugeren selv og bruger hændelser, der allerede logges til audit. Om privatlivspolitikken dækker *visningen*, skal bekræftes, Q8.

Hvorfor audit-tabellerne:
1. De findes allerede, er append-only og har `actor_user_id` og `created_at` med indeks.
2. De dækker præcis "meningsfulde handlinger".
3. De kræver ingen ny indsamling. `runs.requested_by_name` har intet bruger-id og kan ikke bruges.

## 6. Eksport (PDF og CSV)

**PDF: ingen ny afhængighed.** `apps/web/src/server/invoice-pdf.ts` udvides med:

- flere sider
- en tabelhjælper (kolonner, højrestillede tal, gentaget kolonneoverskrift på hver side, sidetal)
- rigtige Helvetica/Helvetica-Bold glyfbredder fra standard-AFM (en tabel i koden) i stedet for 0,52 em, så højrestilling passer

Danske bogstaver virker allerede (WinAnsi). Det holder rapporterne i samme håndskrevne PDF 1.4, som fakturaerne bruger. Den eksisterende `invoicePdf` får regressionstest.

**CSV:**
- Den eksisterende `csv()`/`csvResponse()` genbruges (BOM, semikolon, beskyttelse mod formel-injektion).
- Rapporterne skriver ISO-datoer (`2026-10-01`) og punktum som decimaltegn (`8000.00`).
- Første række er kolonneoverskrifter.
- Beløb står i kroner med to decimaler, og kolonnenavnet siger `ekskl_moms`/`inkl_moms`.

**Fælles:**
- PDF og CSV bygges af **samme rækker** som tabellen på siden (én loader pr. rapport), så e2e kan sammenligne dem.
- Svaret er en streamet `Response` med `Content-Disposition: attachment`.
- Hver eksport skrives i `platform.audit` som `report.exported` med {type, format, from, to, rows}.
- Omsætning og Support er ekskl. moms. Fakturering er inkl. moms.
